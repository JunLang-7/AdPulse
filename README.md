# AdPulse

> 主动发现市场信号，辅助下一步投放决策。

AdPulse 是一个**主动式营销投放决策助手**。

它围绕企业的推广目标与当前方案，结合外部市场信息和自身投放表现，主动发现值得关注的变化，帮助市场与营销人员判断下一步应该延续什么、调整什么、尝试什么，以及什么时候应该暂停。

**当前仓库已交付可运行的 MVP：决策交互子系统覆盖「提醒 → 确认 → 调整方案 → 下一轮」的核心闭环，能力边界与未完成项按下文如实标注。** 已实现卡片轮次、可靠回调、策略快照、异步投递、飞书薄适配、控制台 API/类型化客户端与 Web 界面（任务编辑、效果证据、会话详情、方案假设、市场与竞品事件、发现线索审核、订阅筛选与通知记录）。调整建议已覆盖渠道预算/出价/开关与人群、卖点、内容方向、合作对象的增删，会话详情可展示最早快照到当前的结构化方案差异；三类信号均已实现（见下文「当前阶段」），飞书单聊已实现日汇总与即时/实时推送，任务生命周期（保留期、确认删除、在线清理、最小审计）已按范围收口；仍待完成的是达人/种草投放方式的单独验证及真实广告平台联调（飞书真机验收已部分覆盖，其他推送渠道未接入）；选择提交后的结果跟踪已按 #11 收口，信号初判随定时采集的持续化运行已实现（#222 定时发现循环，默认关闭，生产持续运行待部署验证）。产品范围、用户细分与商业模式仍需验证。

## 为谁解决什么问题

目标用户是需要对推广投入作出判断的市场与营销人员，初步研究范围为山东企业，暂不按行业确定首发客群。

待验证的问题是：市场信息与自身投放结果分散，用户难以及时发现重要变化，也难以将这些变化转化为有依据的下一步投入决策。

AdPulse 希望帮助用户回答：

- 最近发生了哪些与当前推广有关的重要变化？
- 这些变化是否值得影响当前方案？依据是什么？
- 下一步应该调整卖点、内容、人群、渠道、合作对象，还是预算？
- 应该先做什么小规模验证，观察哪些结果，再决定是否继续？

市场动态是输入，**有依据、可控制、可验证的投放决策**才是目标。

## 核心：主动发现，而不是等待提问

用户不必每天先问「今天有什么值得关注」。产品应持续围绕用户的目标与关注范围，主动识别信号，并说明它与当前投放的关系。

重点探索三类信号：

1. **市场变化**：用户需求、竞品动作、内容方向及平台环境中与当前推广有关的变化。
2. **效果变化**：自身投放成本、有效咨询、成交等表现的变化。
3. **假设偏差**：当前方案依赖的判断开始得到支持，或受到新证据挑战。

新信息不一定代表变化，变化也不一定需要行动。没有历史对照时，不应把新发现包装成趋势；证据不足时，应明确说明并建议继续观察或补充核实。

## 方案是判断基线，不是使用门槛

- **已有方案**：理解用户的目标、受众、渠道、预算和正在执行的安排，作为持续观察与提出建议的基线。
- **没有方案**：AI 根据真实业务情况与可用材料生成起步草案，由用户确认；缺失信息应标为未知或待确认，不编造预算、历史效果或经营目标。

方案不是一次生成后就结束的文档，而是持续回答「现在为什么这样投」的依据。

## 用户可控

用户应能够调整关注范围、提醒条件与行动边界。控制台或其他配置入口是待探索的交互方式，不是已经确定的产品形态。

- **关注范围**：关注哪些对象、问题、来源与渠道，排除什么。
- **提醒条件**：哪些事件立即提醒，哪些进入定期汇总；可量化的变化可设置明确阈值。
- **行动边界**：可用预算、可接受的试验范围，以及必须人工确认的事项。

默认方式应能帮助用户开始使用，自定义用于逐步纠偏，而不是要求用户先完成复杂配置。重要性判断不应只依赖一个不可解释的综合分数。

## 初步工作闭环

**建立推广基线 → 持续发现信号 → 人工核实关键依据 → 判断对当前方案的影响 → 形成调整草案与预算安排 → 用户确认行动 → 录入或接收实际结果 → 更新下一轮关注与判断。**

这是业务逻辑，不是页面菜单，也不是必须逐步完成的向导。产品可以先提醒、再补证，用户也可以选择忽略、继续跟踪或暂不调整。

调整建议应交代：

- 发生了什么，以及原始依据在哪里；
- 为什么可能影响当前方案；
- 哪些是事实、哪些是推断，还有哪些不知道；
- 建议改变什么、需要多少投入，以及其他可选方向；
- 如何验证，什么情况下继续、调整或停止。

> 能力边界（当前实现）：可作为建议提出并由内核应用的是渠道预算/出价/开关，以及人群、卖点、内容方向、合作对象的增删。内容方向与合作对象仅记录名称，属于站内基线：不代表已发布、已联系或已投放，也不建模合作阶段与效果指标。附带验证计划的建议在任务口径完整时，会到期关联同一任务的可比证据，只记录指标低于/高于阈值，不推断因果。

## 投放范围与效果边界

同时考虑三类投放方式，并在策略、效果证据与变更词表中分别建模：

- 平台付费广告（`paid_ads`）：投放花费 / 咨询次数 → 单次咨询成本。
- 达人合作（`influencer`）：合作费用 / 互动量 → 单次互动成本。
- 内容种草（`seeding`）：内容成本 / 互动量 → 单次互动成本。

它们可以围绕同一推广目标作出投入选择，但不共用同一种效果衡量方式：证据的指标键、定义、公式和派生成本按投放方式区分；不同口径的指标不能混进同一份证据，不同投放方式的证据不可直接比较。一个任务只设置一套告警口径；点击出价这个旋钮只属于付费广告。

能计算的计算，能比较的比较，无法归因或数据不完整的部分应明确保留。互动量不等于咨询或成交，曝光、互动不能换算成单次咨询成本；归因局限随比较结果与提醒一起展示。指标集是探索阶段的假设，仍需真实使用场景验证，不承诺收益或最优预算。

> 能力边界（当前实现）：三类投放方式目前只建模了指标口径与变更词表（-placement- words 详见架构导览），达人/种草的证据导入、比较与告警走与付费广告相同的通用机制，尚未单独验证；达人合作阶段、费用结算与效果指标仍未实现，README 此处为设计承诺，探索期未实现（见 [投放范围提案](docs/proposals/placement-scope-and-effect-measurement.md)）。

外部市场信息主要帮助发现值得验证的方向；自身真实投放数据主要帮助判断是否继续投入。公开内容不等于竞品真实花费和收益，讨论热度、曝光和点击也不等于利润。

主动发现不等于自动执行。当前定位以建议、草案与人工确认为中心，不默认自动改预算、下单投放或中止合作，不承诺保证收益或找到最优预算。

## 待验证的问题

- 哪一类企业和哪一种投放场景最值得优先服务？实际使用者、受益者与付费者分别是谁？
- 哪些遗漏事件会影响真实决策，用户目前通过什么办法处理？
- 相比舆情监测、投放平台、AI研究工具和人工信息渠道，AdPulse 提供什么额外价值？
- 用户能够提供哪些成本、成交与收益数据？数据缺口如何影响建议？
- 怎样平衡主动提醒与噪音，怎样衡量漏报、误报和建议的实际价值？
- 用户愿意在哪里接收、阅读与处理信息：App、Web、IM、小程序，还是其他方式？
- 用户是否愿意持续使用并付费，服务成本是否可持续？

产品形态应根据真实使用场景决定，不因已有原型或某项采集能力提前锁定。

## 外部信息来源：搜索源聚合与 Agent-Reach

企业官网自动发现由多搜索源聚合完成（百度千帆、Tavily、Exa、Serper、Brave 与默认启用的 Bing RSS；管理员配置与额度见 [搜索源部署指南](docs/search-provider-deployment.md)）。搜索 API 只用于候选定位：首页须验证品牌归属，采集只取标题与链接并遵从 robots，失败换站重试、有失败退避；各源按自然日计额度，用完即停、失败退额，控制台可见用量。不配任何 Key 也能跑（仅免费 Bing 源），但中文召回质量较差。

[Agent-Reach](https://github.com/Panniantong/Agent-Reach) 已部分集成（#167）：Exa 与小红书笔记搜索的结果仍作为**未核验线索**进入待审核列表，人工接受后才入库；未做真机签核与合规签核，仅探索/比赛用途。

是否扩大使用范围，应由目标用户需要的信息、渠道可用性、授权与合规要求、隐私边界和服务成本共同决定，不由工具支持的平台数量反推产品范围。

## 当前阶段

继续验证用户痛点、信号价值与使用场景，同时用已实现的交互子系统检验「提醒 → 选择 → 调整方案 → 下一轮」的技术闭环。三类信号中：效果变化已实现期次比较与阈值告警；市场/竞品事件已实现本人录入与修订；**假设偏差已实现**（方案假设的一等公民模型：AI 辅助生成草案、新证据自动初判、用户确认后变更状态并进入订阅提醒，见 [假设偏差提案](docs/proposals/hypothesis-deviation-signals.md)）。调整建议已覆盖渠道预算/出价/开关与人群、卖点、内容方向、合作对象（README 的调整问题各子项均有对应变更词表），会话详情可展示最早快照到当前的结构化方案差异。

**信号发现已部分实现**：本人登记企业站点时可只填企业名，由搜索源聚合异步查找官网（换站重试；列表页三级兜底：HTML 锚点 / 同域 JSON / sitemap / 站内搜索），采集只取标题与链接；Agent-Reach 的 Exa 与小红书笔记搜索产出**未核验线索**，在控制台逐条接受/拒绝/保留，接受才入库。模型初判每条线索与本人各任务的关联与重要性（待确认），确认后才进入订阅提醒；仍不会自动建事件或自动推送未确认结论。线索来源不再依赖手动 discover：定时发现循环（#222）默认关闭，`DISCOVERY_SCHEDULE_ENABLED=1` 启用后每天 08:00（北京时间）对每个已登记企业官网跑一轮站内索引搜索，新结果进未核验线索并自动排初判 job；生产持续运行待部署开启验证。选择提交后的结果跟踪已按 #11 收口（恢复按钮、幂等复用等偏差见关闭记录）；真实广告平台联调仍未完成，不将工程演示视为产品假设已验证。

**通知与生命周期已实现**：日汇总批次与去重、效果告警与事件的订阅筛选、通知记录与解释（为什么收到/没收到）已交付；事件确认后数秒内推送飞书单聊展示型卡片（仅跳转控制台，不承载操作），可在设置中开关，当前只接飞书、其他渠道未接入不展示。任务生命周期已按范围收口：365 天保留与到期限访、本人确认删除、7 天在线清理、180 天最小审计与手工备份（自动备份、加密与 RPO 明确不做）。

## 开发环境

工程骨架使用 **Bun 1.4.4 管理依赖与 workspace，Node.js 24+ 运行服务和测试**。Bun 不作为服务运行时；请勿使用 `bun --bun` 启动服务。测试为 TypeScript，由 `node --test` 直接运行（类型剥离，不额外编译）。

```bash
bun install --frozen-lockfile
bun run typecheck
bun run build
bun run test
bun run sdk:check
bun run --cwd apps/console typecheck
bun run --cwd apps/console build
```

- 仓库仅维护 `bun.lock`，不再使用 pnpm/npm 锁文件。
- 修改 OpenAPI 后执行 `bun run sdk:generate`。
- 构建后用 `bun run start` 启动 API，或用 `bun run worker` 启动独立 worker；两者脚本均显式调用 Node.js。
- PostgreSQL 集成测试需设置指向专用测试库的 `TEST_DATABASE_URL`；未设置时跳过该项测试。
- Web 控制台：保持 API 运行，另一个终端执行 `cd apps/console && bun run dev`，默认访问 `http://localhost:5173/sessions`。任务可在控制台直接创建（AI 辅助分步填写或直接填表）；完成飞书登录后可先运行 demo 生成记录（需按开发指南注入当前会话 cookie）。
- 控制台使用 Feishu OAuth + PKCE 和服务端 HttpOnly session cookie；运行前需配置 `PUBLIC_ORIGIN` 与 Feishu 应用凭据，生产环境必须使用 HTTPS。详见[开发指南](docs/development.md)。
- 一键部署：`node scripts/deploy.mjs` 完成数据库备份 → 上传 → 远端构建 → 切换 → 健康检查，任一步失败自动回滚到上一版本；部署目标只留在本机 `.deploy.local.env`（不入库），见开发指南 §6.9。
- 搜索源（百度千帆 / Tavily / Exa / Serper / Brave）的密钥申请、额度与排查见 [搜索源部署指南](docs/search-provider-deployment.md)。
- 控制台可保存个人模型连接（加密存储，可测试、设为默认、轮换与吊销），供 AI 辅助填写与线索初判使用；部署也可提供默认模型路由（如 `DEEPSEEK_API_KEY`），见开发指南。
- 真机验收留证默认不入库（含真实环境信息），目录与判读标准见 [docs/acceptance](docs/acceptance/feishu-e2e.md)。
- [开发指南](docs/development.md)：环境变量、两轮演示、飞书配置、独立 worker 与数据库测试。
- [架构导览](docs/architecture.md)：当前模块边界、出入站契约、一致性和已知限制。
